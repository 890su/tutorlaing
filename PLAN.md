# План реализации MVP

Документ описывает реализацию первой рабочей вертикали. Он не заменяет product discovery из [ROADMAP.md](./ROADMAP.md): до написания сложного движка нужно проверить сценарии вручную.

## Текущее состояние реализации

На 2026-08-01 готова Telegram-first техническая alpha:

- код находится в Git-репозитории 890su/tutorlaing;
- реализованы 8 сценариев и полный текстовый учебный цикл;
- адаптация v0 использует объяснимые правила без LLM;
- данные хранятся в SQLite, доступны consent, allowlist и удаление;
- контейнер публикуется в GHCR через GitHub Actions;
- локально проходят 16 автоматических тестов;
- Telegram Bot API и существующий бот @hermes890bot доступны;
- прямой SSH с рабочей станции недоступен, но серверный MCP SSH-контур работает;
- очистка старого runtime и первый deploy на srv-150 ещё не выполнены.

Открытые gates: review польского контента, dogfooding, внешние пользователи и фактические alpha-метрики.

## 1. Результат первой версии

Пользователь должен суметь пройти один полный цикл:

1. выбрать ближайшую жизненную ситуацию;
2. выполнить короткую диагностическую задачу;
3. получить одно понятное объяснение главного затруднения;
4. пройти микротренировку;
5. повторить задачу с меньшим количеством подсказок;
6. получить назначенную проверку через 2–7 дней;
7. отметить, помогла ли подготовка в реальной жизни.

Если этот путь нельзя пройти целиком, MVP ещё не готов независимо от количества реализованных экранов.

## 2. Рекомендуемый технический контур

Для быстрого тестирования рекомендуется mobile-first web/PWA вместо нативных приложений.

Базовый вариант стека:

- TypeScript;
- React-фреймворк с серверными маршрутами;
- PostgreSQL;
- простой SQL/query layer или ORM;
- объектное хранилище только для аудио, которое пользователь разрешил сохранить;
- очередь фоновых задач для транскрипции и анализа;
- абстракции над LLM, speech-to-text и text-to-speech провайдерами;
- продуктовая аналитика с псевдонимизированным идентификатором;
- error tracking и структурированные серверные логи.

Конкретные поставщики и версии выбираются непосредственно перед началом кода после небольших spike-тестов. Бизнес-логика не должна зависеть от формата ответа одного AI-провайдера.

## 3. Архитектурные границы

```text
Mobile Web / PWA
       │
       ▼
Application API
       ├── Identity & consent
       ├── Scenario session
       ├── Diagnostic rules
       ├── Practice & review scheduler
       ├── Progress evidence
       └── Analytics events
       │
       ├── PostgreSQL
       ├── Curated content
       └── AI gateway
              ├── LLM
              ├── Speech-to-text
              └── Text-to-speech
```

### Обязательные правила

- Сценарий и его учебные цели задаются курируемыми данными, а не генерируются LLM с нуля.
- LLM играет роль собеседника и формирует кандидаты обратной связи, но итог ограничивается схемой и правилами.
- Каждое автоматическое решение сохраняет причину, версию prompt/model и исходные наблюдения.
- При сбое AI пользователь получает восстановимый сценарий, а не теряет всю сессию.
- Аудио и транскрипт имеют разные политики хранения.
- Контент отделён от кода, чтобы его мог проверять преподаватель польского.

## 4. Минимальная модель данных

### User

- язык интерфейса;
- срок проживания в Польше;
- самооценка и результаты короткой диагностики;
- жизненные цели;
- предпочтительный режим: текст/голос;
- согласия на обработку и хранение данных.

### Goal

- категория: жильё, здоровье, работа, urząd, покупки, общение;
- описание реального события;
- предполагаемая дата;
- важность и самооценка уверенности.

### Scenario

- контекст и роль пользователя;
- коммуникативный результат;
- ожидаемые реплики собеседника;
- целевые chunks и конструкции;
- варианты сложности;
- допустимые подсказки;
- прагматические замечания;
- ограничения безопасности;
- версия и статус ручной проверки.

### SessionAttempt

- сценарий и его версия;
- режим ввода;
- реплики и временные метки;
- использованные подсказки;
- завершённость задачи;
- версия AI-конфигурации;
- согласованный срок хранения исходных данных.

### Observation

- наблюдаемый факт, а не общий ярлык;
- тип затруднения;
- затронутый chunk/навык;
- серьёзность;
- уверенность классификатора;
- источник: правило, AI или ручная проверка;
- доказательство из попытки.

### LearningItem

- слово, chunk, конструкция или тип реплики;
- представление для текста и аудио;
- связи со сценариями;
- состояния понимания и воспроизведения;
- история повторений.

### Review

- назначенное время;
- причина назначения;
- требуемая форма ответа;
- уровень подсказок;
- результат и самостоятельность;
- следующий интервал.

### RealWorldOutcome

- состоялась ли ситуация;
- удалось ли выполнить задачу;
- что оказалось неожиданным;
- самооценка уверенности после события;
- свободный комментарий.

## 5. Модель диагностики v0

На первом этапе не нужен универсальный knowledge graph. Для каждого сценария задаются ожидаемые коммуникативные действия, например:

- начать разговор;
- объяснить потребность;
- понять один из типичных вопросов;
- дать достаточный ответ;
- запросить уточнение;
- корректно завершить разговор.

### Алгоритм выбора bottleneck

1. Зафиксировать наблюдаемые затруднения.
2. Отбросить замечания с низкой уверенностью.
3. Повысить приоритет ошибки, мешающей выполнить задачу.
4. Повысить приоритет повторяющегося затруднения.
5. Повысить приоритет элемента, нужного для ближайшего события.
6. Выбрать одну основную и максимум две дополнительные рекомендации.
7. Сохранить человекочитаемое объяснение выбора.

Пример простой оценки:

```text
priority = task_blocking * 4
         + repeated * 3
         + goal_relevance * 2
         + teachability_now
         - classifier_uncertainty * 3
```

Коэффициенты являются начальными правилами и меняются только после аудита ошибок. Не следует обучать модель на малом и субъективном наборе dogfooding-данных.

## 7. События аналитики MVP

Минимальный словарь:

- `onboarding_completed`;
- `goal_created`;
- `scenario_started`;
- `hint_used`;
- `scenario_completed`;
- `observation_created`;
- `bottleneck_selected`;
- `practice_started`;
- `practice_completed`;
- `review_scheduled`;
- `review_completed`;
- `real_world_outcome_reported`;
- `voice_processing_failed`;
- `ai_fallback_used`;
- `account_data_deleted`.

Для событий задаются версия схемы, timestamp, pseudonymous user ID, scenario version и session ID. Полный текст реплик не отправляется в обычную продуктовую аналитику.

## 8. Тестовая стратегия

### Автоматические тесты

- правила выбора bottleneck;
- расчёт следующего повторения;
- уровни подсказок;
- валидация контента и AI-схем;
- права доступа и удаление данных;
- полный happy path одной сессии;
- восстановление после таймаута AI.

### Педагогический regression-набор

Для каждого сценария хранится набор примеров:

- успешный ответ разными словами;
- грамматически несовершенный, но коммуникативно достаточный ответ;
- ответ с критическим непониманием;
- транскрипт с ошибкой распознавания;
- смешение польского и русского;
- просьба о пояснении;
- нерелевантный или небезопасный ответ AI.

Цель — не оценивать язык по одному «правильному предложению» и не наказывать пользователя за допустимую вариативность.

### Ручной контроль

- первые 100 завершённых сессий просматриваются выборочно с согласия пользователей;
- минимум 20% AI-рекомендаций получают ручную оценку в alpha;
- польский контент проверяется до публикации;
- спорные рекомендации помечаются и добавляются в regression-набор.

## 9. Definition of Done для alpha

Alpha готова к внешним пользователям, когда:

- полный учебный цикл работает на мобильном устройстве;
- доступны минимум 8 проверенных сценариев;
- пользователь понимает, почему назначена конкретная тренировка;
- отложенная проверка использует изменённый контекст;
- есть аналитика воронки и учебного результата;
- AI-сбой не блокирует завершение сессии;
- голос можно отключить без разрушения продукта;
- стоимость внешних вызовов наблюдаема;
- пользователь может удалить свои данные;
- критические сценарии имеют ручную проверку формулировок;
- проведён тест минимум с 5 людьми, не участвовавшими в разработке.

## 10. Первые два спринта после discovery

### Sprint 1: текстовая вертикаль

Цель: один пользователь проходит один сценарий от цели до немедленной повторной попытки.

- каркас приложения и БД;
- профиль и выбор цели;
- формат курируемого сценария;
- текстовый диалог;
- фиксация подсказок и действий;
- rule-based наблюдения;
- одна микротренировка;
- повтор сценария;
- базовые события и тест happy path.

### Sprint 2: отложенная проверка и контролируемый AI

Цель: замкнуть цикл во времени и начать измерять перенос.

- очередь повторений;
- изменённые варианты сценария;
- AI gateway и строгая схема;
- объяснение bottleneck;
- дневник реального результата;
- regression-набор;
- управление согласиями и удаление данных;
- cost/latency monitoring;
- внутренний dogfooding и исправление блокирующих проблем.

## 11. Реестр ключевых рисков

| Риск | Ранний тест | Реакция |
|---|---|---|
| Пользователю проще открыть переводчик | Интервью и concierge-тест | Фокус на репетиции ответа собеседника и переносе, а не переводе фразы |
| AI даёт лишние или неверные исправления | Ручной аудит и regression-набор | Ограничить категории, число замечаний и свободу генерации |
| ASR плохо понимает акцент | Spike на реальных устройствах | Текстовый fallback, confidence threshold, отсутствие штрафа |
| Авторский опыт не репрезентативен | Внешняя когорта | Сегментация результатов, запрет обобщений из n=1 |
| Пользователь не возвращается на проверку | Concierge и alpha | Привязать напоминание к цели и показать смысл проверки |
| Контентная работа не масштабируется | Измерение времени на сценарий | Шаблоны, переиспользуемые chunks, инструменты редактора |
| Голосовой AI слишком дорог | Учёт стоимости по сессии | Лимиты, каскад моделей, короткие сессии, пакетная цена |
| Метрика показывает игру, а не навык | Новый контекст и real-world report | Оценивать перенос без подсказок |
| Ошибка в чувствительном сценарии | Ручная экспертная проверка | Ограничения, дисклеймеры, исключение советов вне языка |

## 12. Решения, которые пока не принимаются

До результатов concierge/alpha не фиксируются:

- финальный бренд;
- нативное мобильное приложение;
- конкретный AI-провайдер как постоянная зависимость;
- сложный FSRS/knowledge tracing;
- официальный CEFR placement;
- безлимитная подписка;
- B2B-кабинет;
- поддержка других языков.

Такой порядок оставляет возможность изменить продукт без дорогой переработки, если реальное поведение мигрантов не подтвердит исходные предположения.
