# План реализации MVP

Документ описывает реализацию первой рабочей вертикали. Он не заменяет product discovery из [ROADMAP.md](./ROADMAP.md): до написания сложного движка нужно проверить сценарии вручную.

## Текущее состояние реализации

На 2026-08-02 готова Telegram-first техническая alpha:

- код находится в Git-репозитории 890su/tutorlaing;
- реализованы 8 сценариев и полный текстовый учебный цикл;
- production использует OpenAI GPT-5.6 Sol как основной AI, Gemini 3.5 Flash
  как второй provider и объяснимые rule-based правила как независимый fallback;
- доступны natural response, варианты по регистрам, перевод по запросу,
  grammar drill-down и три независимые языковые настройки;
- язык объяснений/перевода выбирается из `ru/uk/en/pl`, изучаемый — из
  `pl/en`; для обоих target доступны 8 бытовых ситуаций;
- работают AI-наборы из 5 контекстных упражнений минимум 3 типов, локальная
  проверка вариантов и AI-проверка свободного ответа;
- доступны opt-in напоминания от мягких до агрессивных с quiet hours,
  паузой на день, защитой от дублей и доставкой следующего scenario/drill item;
- после каждого ответа следующий шаг ждёт кнопку или scheduled delivery, а
  одно срабатывание scheduler отправляет только одно задание;
- основные экраны используют единый маршрутный UI и одну главную кнопку;
- рабочие AI-ключи хранятся только в защищённом Tutorlaing `.env` без
  публикации значений;
- данные хранятся в SQLite, доступны consent, allowlist и удаление;
- контейнер публикуется в GHCR через GitHub Actions;
- локально проходят 73 автоматических теста;
- production работает на @brnai_bot через защищённый webhook;
- прямой SSH с рабочей станции недоступен, но серверный MCP SSH-контур работает;
- runtime развёрнут из GitHub/GHCR в /home/admin890brain/services/tutorlaing;
- публичный и локальный health, webhook secret, команды и synthetic update проверены;
- старые n8n, Google MCP и Twenty CRM контейнеры и volumes удалены;
- на VM оставлены только Tutorlaing и management MCP bridge;
- заполнение корневого диска снижено с 88% до 70%.

Открытые gates: review польского контента, dogfooding, внешние пользователи и фактические alpha-метрики.

## 1. Результат первой версии

Пользователь должен суметь пройти один полный цикл:

1. выбрать ближайшую жизненную ситуацию;
2. выполнить короткую диагностическую задачу;
3. получить одно понятное объяснение главного затруднения;
4. пройти микротренировку;
5. повторить задачу с меньшим количеством подсказок;
6. получить назначенную проверку через 2–7 дней;
7. отметить, помогла ли подготовка в реальной жизни.

Если этот путь нельзя пройти целиком, MVP ещё не готов независимо от количества реализованных экранов.

## 2. Рекомендуемый технический контур

Для быстрого тестирования рекомендуется mobile-first web/PWA вместо нативных приложений.

Базовый вариант стека:

- TypeScript;
- React-фреймворк с серверными маршрутами;
- PostgreSQL;
- простой SQL/query layer или ORM;
- объектное хранилище только для аудио, которое пользователь разрешил сохранить;
- очередь фоновых задач для транскрипции и анализа;
- абстракции над LLM, speech-to-text и text-to-speech провайдерами;
- продуктовая аналитика с псевдонимизированным идентификатором;
- error tracking и структурированные серверные логи.

Конкретные поставщики и версии выбираются непосредственно перед началом кода после небольших spike-тестов. Бизнес-логика не должна зависеть от формата ответа одного AI-провайдера.

## 3. Архитектурные границы

```text
Mobile Web / PWA
       │
       ▼
Application API
       ├── Identity & consent
       ├── Scenario session
       ├── Diagnostic rules
       ├── Practice & review scheduler
       ├── Progress evidence
       └── Analytics events
       │
       ├── PostgreSQL
       ├── Curated content
       └── AI gateway
              ├── LLM
              ├── Speech-to-text
              └── Text-to-speech
```

### Обязательные правила

- Сценарий и его учебные цели задаются курируемыми данными, а не генерируются LLM с нуля.
- LLM играет роль собеседника и формирует кандидаты обратной связи, но итог ограничивается схемой и правилами.
- Каждое автоматическое решение сохраняет причину, версию prompt/model и исходные наблюдения.
- При сбое AI пользователь получает восстановимый сценарий, а не теряет всю сессию.
- Аудио и транскрипт имеют разные политики хранения.
- Контент отделён от кода, чтобы его мог проверять преподаватель польского.

## 4. Минимальная модель данных

### User

- язык заданий и объяснений (`instruction_language`);
- язык перевода по запросу (`translation_language`);
- изучаемый язык (`target_language`): польский или английский;
- срок проживания в Польше;
- самооценка и результаты короткой диагностики;
- жизненные цели;
- предпочтительный режим: текст/голос;
- согласия на обработку и хранение данных.

### Goal

- категория: жильё, здоровье, работа, urząd, покупки, общение;
- описание реального события;
- предполагаемая дата;
- важность и самооценка уверенности.

### Scenario

- контекст и роль пользователя;
- коммуникативный результат;
- ожидаемые реплики собеседника;
- целевые chunks и конструкции;
- варианты сложности;
- допустимые подсказки;
- прагматические замечания;
- ограничения безопасности;
- версия и статус ручной проверки.

### SessionAttempt

- сценарий и его версия;
- режим ввода;
- реплики и временные метки;
- использованные подсказки;
- завершённость задачи;
- версия AI-конфигурации;
- согласованный срок хранения исходных данных.

### AIAnalysis

- ссылка на попытку, сообщение и анализируемый фрагмент;
- вид операции: оценка, naturalness, варианты, перевод или грамматика;
- структурированный результат без скрытой цепочки рассуждений;
- provider, model, версия prompt и JSON schema;
- latency, usage, статус, confidence и признак fallback;
- пользовательская оценка полезности;
- срок хранения и каскадное удаление вместе с пользователем.

### Observation

- наблюдаемый факт, а не общий ярлык;
- тип затруднения;
- затронутый chunk/навык;
- серьёзность;
- уверенность классификатора;
- источник: правило, AI или ручная проверка;
- доказательство из попытки.

### LearningItem

- слово, chunk, конструкция или тип реплики;
- представление для текста и аудио;
- связи со сценариями;
- состояния понимания и воспроизведения;
- история повторений.

### Review

- назначенное время;
- причина назначения;
- требуемая форма ответа;
- уровень подсказок;
- результат и самостоятельность;
- следующий интервал.

### RealWorldOutcome

- состоялась ли ситуация;
- удалось ли выполнить задачу;
- что оказалось неожиданным;
- самооценка уверенности после события;
- свободный комментарий.

## 5. Модель диагностики v0

На первом этапе не нужен универсальный knowledge graph. Для каждого сценария задаются ожидаемые коммуникативные действия, например:

- начать разговор;
- объяснить потребность;
- понять один из типичных вопросов;
- дать достаточный ответ;
- запросить уточнение;
- корректно завершить разговор.

### Алгоритм выбора bottleneck

1. Зафиксировать наблюдаемые затруднения.
2. Отбросить замечания с низкой уверенностью.
3. Повысить приоритет ошибки, мешающей выполнить задачу.
4. Повысить приоритет повторяющегося затруднения.
5. Повысить приоритет элемента, нужного для ближайшего события.
6. Выбрать одну основную и максимум две дополнительные рекомендации.
7. Сохранить человекочитаемое объяснение выбора.

Пример простой оценки:

```text
priority = task_blocking * 4
         + repeated * 3
         + goal_relevance * 2
         + teachability_now
         - classifier_uncertainty * 3
```

Коэффициенты являются начальными правилами и меняются только после аудита ошибок. Не следует обучать модель на малом и субъективном наборе dogfooding-данных.

## 8. Тестовая стратегия

### Автоматические тесты

- правила выбора bottleneck;
- расчёт следующего повторения;
- уровни подсказок;
- валидация контента и AI-схем;
- права доступа и удаление данных;
- полный happy path одной сессии;
- восстановление после таймаута AI.

### Педагогический regression-набор

Для каждого сценария хранится набор примеров:

- успешный ответ разными словами;
- грамматически несовершенный, но коммуникативно достаточный ответ;
- ответ с критическим непониманием;
- транскрипт с ошибкой распознавания;
- смешение польского и русского;
- просьба о пояснении;
- нерелевантный или небезопасный ответ AI.

Цель — не оценивать язык по одному «правильному предложению» и не наказывать пользователя за допустимую вариативность.

### Ручной контроль

- первые 100 завершённых сессий просматриваются выборочно с согласия пользователей;
- минимум 20% AI-рекомендаций получают ручную оценку в alpha;
- польский контент проверяется до публикации;
- спорные рекомендации помечаются и добавляются в regression-набор.

## 9. Definition of Done для alpha

Alpha готова к внешним пользователям, когда:

- полный учебный цикл работает на мобильном устройстве;
- доступны минимум 8 проверенных сценариев;
- пользователь понимает, почему назначена конкретная тренировка;
- отложенная проверка использует изменённый контекст;
- есть аналитика воронки и учебного результата;
- AI-сбой не блокирует завершение сессии;
- голос можно отключить без разрушения продукта;
- стоимость внешних вызовов наблюдаема;
- пользователь может удалить свои данные;
- критические сценарии имеют ручную проверку формулировок;
- проведён тест минимум с 5 людьми, не участвовавшими в разработке.

## 10. Первые два спринта после discovery

### Sprint 1: текстовая вертикаль

Цель: один пользователь проходит один сценарий от цели до немедленной повторной попытки.

- каркас приложения и БД;
- профиль и выбор цели;
- формат курируемого сценария;
- текстовый диалог;
- фиксация подсказок и действий;
- rule-based наблюдения;
- одна микротренировка;
- повтор сценария;
- базовые события и тест happy path.

### Sprint 2: отложенная проверка и контролируемый AI

Цель: замкнуть цикл во времени и начать измерять перенос.

- очередь повторений;
- изменённые варианты сценария;
- AI gateway и строгая схема;
- объяснение bottleneck;
- дневник реального результата;
- regression-набор;
- управление согласиями и удаление данных;
- cost/latency monitoring;
- внутренний dogfooding и исправление блокирующих проблем.

## 11. Реестр ключевых рисков

| Риск | Ранний тест | Реакция |
|---|---|---|
| Пользователю проще открыть переводчик | Интервью и concierge-тест | Фокус на репетиции ответа собеседника и переносе, а не переводе фразы |
| AI даёт лишние или неверные исправления | Ручной аудит и regression-набор | Ограничить категории, число замечаний и свободу генерации |
| ASR плохо понимает акцент | Spike на реальных устройствах | Текстовый fallback, confidence threshold, отсутствие штрафа |
| Авторский опыт не репрезентативен | Внешняя когорта | Сегментация результатов, запрет обобщений из n=1 |
| Пользователь не возвращается на проверку | Concierge и alpha | Привязать напоминание к цели и показать смысл проверки |
| Контентная работа не масштабируется | Измерение времени на сценарий | Шаблоны, переиспользуемые chunks, инструменты редактора |
| Голосовой AI слишком дорог | Учёт стоимости по сессии | Лимиты, каскад моделей, короткие сессии, пакетная цена |
| Метрика показывает игру, а не навык | Новый контекст и real-world report | Оценивать перенос без подсказок |
| Ошибка в чувствительном сценарии | Ручная экспертная проверка | Ограничения, дисклеймеры, исключение советов вне языка |

## 12. Решения, которые пока не принимаются

До результатов concierge/alpha не фиксируются:

- финальный бренд;
- нативное мобильное приложение;
- конкретный AI-провайдер как постоянная зависимость;
- сложный FSRS/knowledge tracing;
- официальный CEFR placement;
- безлимитная подписка;
- B2B-кабинет;
- поддержка других языков.

Такой порядок оставляет возможность изменить продукт без дорогой переработки, если реальное поведение мигрантов не подтвердит исходные предположения.

## 13. План AI-расширения Telegram alpha

### 13.1. Целевой пользовательский опыт

После каждого содержательного ответа пользователя бот показывает короткую карточку:

1. выполнена ли коммуникативная задача;
2. что в ответе уже хорошо и понятно;
3. максимум 1–2 важных исправления;
4. как тот же ответ прозвучал бы естественнее;
5. кнопки для углубления без перегрузки основного диалога.

Кнопки под карточкой:

- `✨ Естественнее` — одна рекомендуемая переформулировка;
- `🔁 Другие варианты` — до трёх естественных вариантов с пометками регистра;
- `📚 Объяснить грамматику` — всё предложение или выбранный фрагмент;
- `🌐 Перевести` — перевод текущего задания либо комментария;
- `👍 Полезно / 👎 Не полезно` — сигнал качества для ручного аудита.

AI не должен превращать любой ответ в литературный идеал. Если смысл понятен и
задача решена, грамматические замечания помечаются как улучшения, а не как
провал. Приоритет: результат → естественность → грамматическая точность.

### 13.2. Три независимые языковые настройки

В `/settings` и главном меню добавить:

- **язык заданий и объяснений** — язык интерфейса, инструкций и AI-комментариев;
- **язык перевода** — язык, на который переводятся задания и комментарии по
  запросу; по умолчанию совпадает с языком объяснений;
- **изучаемый язык** — язык диалогов и пользовательских ответов.

Языки объяснений и перевода: русский, украинский, английский и польский.
Целевые языки: польский и английский. Каждый target имеет отдельный набор
курируемых сценариев; AI-анализ и очередь повторов сохраняют target language,
чтобы не переносить польскую фразу в английский drill после переключения.

Основной сценарий остаётся в польском. Перевод никогда не раскрывается
автоматически: пользователь нажимает `🌐 Перевести задание` или
`🌐 Перевести комментарий`. Событие перевода учитывается как использованная
подсказка и может влиять на оценку самостоятельности, но не на грамматическую
оценку ответа.

### 13.3. Разбор выбранной фразы в Telegram

Telegram не позволяет приложению получить произвольное визуальное выделение
внутри сообщения. Поэтому после нажатия `📚 Объяснить грамматику` бот предлагает:

- `Всё предложение`;
- 2–5 смысловых chunks, выделенных AI в последнем ответе;
- `Ввести свой фрагмент` или ответить на сообщение командой `/grammar <фраза>`.

В callback передаётся короткий `analysis_id` и номер chunk, а не сам текст:
это укладывается в лимит Telegram callback data. Выбранный фрагмент должен быть
подстрокой последнего сообщения либо явно введён пользователем. Ответ содержит:

- перевод значения в данном контексте;
- роль конструкции и форму слов;
- почему использован именно этот падеж, вид, время или порядок слов;
- один короткий контрастный пример;
- распространённую ошибку русскоязычного ученика, только если она релевантна.

### 13.4. AI pipeline

Для каждого ответа запускается один основной structured-output запрос к AI.
В него передаются только текущий курируемый сценарий, его коммуникативная цель,
последняя реплика собеседника, ответ пользователя и языковые настройки.

Ожидаемая схема результата:

```text
task_achieved: boolean
score: 0..1
confidence: 0..1
meaning_gaps[]
critical_corrections[]
optional_improvements[]
natural_response
alternatives[{text, register, nuance}]
grammar_chunks[{text, label}]
pragmatic_note
explanation
```

Технические правила:

- первый provider — Gemini; рабочая модель на имеющемся ключе —
  `gemini-3.5-flash`. Pro-модели проверены, но имеют нулевую квоту до
  подключения billing;
- код зависит от внутреннего `AIProvider`, а не от Gemini response format;
- JSON валидируется до использования, неизвестные поля игнорируются;
- пользовательский текст передаётся как данные и не может менять системные
  инструкции или rubric сценария;
- rule-based оценка считается параллельно и используется при timeout, 429,
  5xx, невалидном JSON или выключенном feature flag;
- повторный запрос разрешён один раз; сессия никогда не теряется из-за AI;
- translation, variants и grammar могут быть отдельными запросами по кнопке;
- повторный одинаковый запрос к неизменному сообщению можно кэшировать ради
  скорости и согласованности, а не ради искусственного ограничения AI.

Пользователь попросил не экономить на качестве: AI вызывается для каждого
содержательного ответа. Защитные ограничения по длине ввода, timeout,
конкурентности и rate limit всё равно обязательны против зависания и злоупотреблений.

### 13.5. Секреты и приватность

- Рабочий `GEMINI_API_KEY` найден в серверной конфигурации прежнего Brainless и
  проверен с VM; локальная копия с рабочей станции получает 403 и не считается
  production-источником.
- При реализации ключ копируется server-to-server в защищённый `.env`
  Tutorlaing без печати в терминал, логи, GitHub Actions или документацию.
- В репозиторий добавляются только `AI_PROVIDER`, `GEMINI_MODEL` и пустой
  `GEMINI_API_KEY` в `.env.example`.
- До первого AI-вызова существующим пользователям показывается обновлённое
  согласие: их учебная реплика и минимальный контекст будут отправляться Google.
- В prompt не отправляются Telegram ID, имя, история других сценариев и
  несвязанные персональные данные.
- `/delete_me` удаляет также AI analyses, chunks, переводы и пользовательские
  оценки; полные prompts/responses не попадают в продуктовую аналитику.

## 14. Закрепление, напоминания и Telegram UI — реализовано 2026-08-01

### 14.1. Учебная модель закрепления

После сценария AI строит не случайный quiz, а короткий набор по последнему
затруднению пользователя. Базовая сессия содержит 5 заданий и чередует:

1. `choose_form` — выбрать форму по роду, числу, лицу или падежу;
2. `fill_ending` — восстановить окончание в контексте;
3. `complete_sentence` — вставить одно или несколько слов в требуемой форме;
4. `transform` — изменить лицо, род, число, время или вежливый регистр;
5. `word_order` — собрать естественный порядок слов;
6. `correct_error` — найти и исправить одну типичную ошибку;
7. `meaning_choice` — различить близкие по форме, но разные по смыслу варианты;
8. `free_recall` — воспроизвести полезный chunk без вариантов ответа.

В одной пятёрке не должно быть пяти одинаковых cloze-вопросов. Минимум два
задания требуют активного воспроизведения, минимум одно проверяет форму в новом
контексте, а последнее возвращает материал в жизненную реплику. Ошибка меняет
следующий набор: тот же навык возвращается другим типом задания, а не точной
копией вопроса.

AI возвращает строгую схему: `type`, `skill`, `prompt`, `context`, `options`,
`correct_answer`, `accepted_answers`, `explanation`, `hint`, `difficulty`.
Multiple-choice проверяется локально; свободный ответ проверяется AI по
сохранённой цели и допустимым формам. Итог AI не должен штрафовать за другой
правильный вариант.

### 14.2. Reminder modes

Напоминания являются opt-in и соблюдают `Europe/Warsaw` и quiet hours 22:00–08:00.

| Режим | Частота | Поведение |
|---|---:|---|
| Выключены | 0 | Бот пишет только в ответ на действия пользователя |
| Мягкие | до 1/день | Только просроченное повторение или один короткий prompt |
| Обычные | до 2/день | Утро/вечер, повторение или 3-минутное закрепление |
| Интенсивные | до 4/день | Задания в течение дня с интервалом не менее 3 часов |
| Агрессивные | до 6/день | Непосредственные микро-задания в разрешённые часы |

После ответа scenario или drill следующий item ставится в очередь. Пользователь
может нажать `Следующее задание` сразу либо закрыть чат; scheduler доставит
ровно один queued item в ближайший слот выбранного режима. Неотвеченное drill
задание повторяется, отвеченное — продвигается. Активные scenario/practice/review
не прерываются. Кнопки `Пауза на сегодня` и `Изменить режим` доступны из
scheduled drill. Ошибка доставки не создаёт бесконечные повторы.

### 14.3. Telegram UI system

Направление: польская городская навигация — короткие маршрутные карточки вместо
длинных учебных полотен. Ограничения Telegram используются осознанно:

- один экран — один вопрос или решение;
- одна визуально первая кнопка продолжает основной путь;
- четыре стабильных символа: `▶` начать, `🧩` закрепить, `↻` повторить,
  `⚙` настроить;
- заголовок сообщает режим и прогресс: `ZAKOTWICZENIE · 2/5`;
- кнопка `← Назад` всегда находится последней и означает одно и то же;
- системные слова AI, JSON, bottleneck, callback и provider не видны ученику;
- feedback разделён на `Получилось`, `Поправить` и `Почему`, без стены текста;
- destructive action всегда вынесен в отдельное подтверждение.

Фирменный элемент — маршрут
`СИТУАЦИЯ → ФРАЗА → ЗАКРЕПЛЕНИЕ → ПОВТОР`, где текущий этап выделяется
маркером `●`. Он должен появляться в начале сессии и после её завершения.

## 15. Локализованный learner workspace и прогресс — реализовано 2026-08-02

### 15.1. Семантика языковых настроек

`instruction_language` управляет языком заданий, объяснений, меню, кнопок и
основных системных подписей. `translation_language` не дублирует интерфейс: он
используется для полного перевода по явной кнопке и коротких сложных сносок.
`target_language` определяет изучаемый материал и изолирует sessions, reviews,
AI analyses и drills польского от английского.

Профиль дополнен `learner_level` A0–C1. Это рабочая оценка сложности, которую
ученик может изменить вручную; приложение явно не называет её официальным
CEFR. Для текста на target language Gemini может вернуть до двух exact-substring
сносок. Минимальная сложность сноски — два шага выше уровня ученика
(`A1 → B1`, `A2 → B2`, `B1 → C1`); если подходящих единиц нет, блок отсутствует.

### 15.2. Одна карточка вместо ленты экранов

В профиле хранится `workspace_message_id`. Нажатия на inline-кнопки вызывают
`editMessageText` текущей карточки:

1. ситуация и текущая реплика;
2. результат ответа;
3. вкладки `Ответ / Варианты / Грамматика / Перевод`;
4. подсказка и возврат к заданию;
5. следующий шаг, drill item или экран завершения;
6. home, settings, reminders и progress.

После свободного текстового ответа бот создаёт ровно одну новую feedback-card
под сообщением ученика: редактирование старой карточки оставило бы результат
выше ответа и сделало бы его незаметным. Все вкладки этого feedback и переход
`Далее` снова работают через edit. Если сообщение нельзя отредактировать, бот безопасно создаёт новое и делает
его текущим workspace. Scheduled reminder всегда создаёт ровно одно новое
сообщение, чтобы Telegram показал notification, после чего дальнейшие действия
снова редактируют уже его.

### 15.3. Защита от повторной доставки

Scheduler сначала атомарно меняет `reminder_next_at`, проверяя прежнее значение
в `WHERE`. Поэтому два процесса или два tick со старым snapshot не могут оба
зарезервировать один слот. `pending_assignment` забирается транзакционно, а
один scheduled вызов материализует только одну единицу: следующий scenario
step, practice, review либо один drill item.

События `ui_message_sent` и `ui_message_edited` позволяют проверить реальное
соотношение новых сообщений и переходов. Regression tests фиксируют правила:
один свободный ответ создаёт ровно одну feedback-card; inline-переход не
увеличивает число сообщений; scheduled delivery увеличивает его ровно на один;
stale scheduler reservation отклоняется.

### 15.4. Прогресс и формирование ближайшего плана

Экран `/progress` строится только по наблюдаемым данным текущего target language:

- `закреплено` — есть завершённый review с достаточной оценкой;
- `нужно проработать` — сценарий пройден, но нет подтверждённого переноса или
  есть ожидающий review;
- `ближайший план` — сначала незакреплённые ситуации, затем ещё не начатые,
  максимум три пункта;
- рабочий уровень показывается отдельно от фактических учебных свидетельств.

Следующий этап не меняется автоматически без данных: после founder dogfooding
нужно проверить понятность карточки, полезность сносок, качество польского и
соответствие предложенного плана реальным целям мигранта. Затем — закрытая
когорта 10–20 пользователей и ручной педагогический audit до open beta.

## 17. Интерактивная языковая мастерская — реализовано 2026-08-02

Главное меню ведёт в `/tools`, где режим выбирается по намерению ученика, а не
по внутреннему типу упражнения:

1. `Мои ошибки` продолжает персональное закрепление по последнему AI-разбору.
2. `Карточки` выбирают пять курируемых chunks текущего target language. Каждая
   карточка показывает четыре значения, отдельную кнопку `Не помню`, после
   ответа — правильный смысл и короткое объяснение употребления.
3. `Перевести →` принимает произвольную фразу на translation language и
   возвращает основной естественный вариант на target language плюс до трёх
   alternatives по регистру. `← Понять фразу` выполняет обратное направление.
4. `Сценарий` позволяет выбрать одну из восьми тем и получить пять разных
   упражнений: понимание, перевод, форма в контексте и самостоятельная реплика.

Карточки и тематические packs используют существующие `drill_sessions` и
`drill_items`: одинаково переживают restart, работают с кнопкой `Далее` и могут
продолжаться scheduler без пачки сообщений. В `drill_sessions.mode` хранится
источник тренировки; `users.toolkit_input_mode` существует только пока бот ждёт
фразу для перевода. Переводы сохраняются в `ai_analyses` с operation
`phrase_translation`, без Telegram ID в AI prompt.

AI-контракты дополнены `generate_toolkit_pack` и `translate_with_variants` со
строгими JSON schemas. Flashcard pack отклоняется, если содержит не пять
карточек или не четыре варианта на карточку. Тематический pack сохраняет
требование минимум трёх типов и двух active-recall заданий. Полный набор — 57
тестов, включая upgrade существующей SQLite-базы.

## 19. Независимые инструменты поверх занятия — реализовано 2026-08-02

Мастерская больше не конкурирует с основным курсом за один learner state.
Выбрана модель временного overlay: быстрый инструмент можно открыть из scenario,
review, waiting или другого drill, не помечая исходную активность abandoned.

Реализовано:

1. [x] Перевод хранит только `toolkit_input_mode`; `stage`, session, review и
   drill остаются без изменений. После результата доступна явная кнопка
   `Вернуться к занятию`.
2. [x] Перед карточками, тематическим pack или `Мои ошибки` основная активность
   сохраняется в `users.suspended_activity_json`, а live-поля очищаются от
   основного контекста.
3. [x] Tool drill создаётся с `replace_active=False`: предыдущий drill остаётся
   active и снова становится current после завершения временного.
4. [x] Complete и stop атомарно восстанавливают snapshot в той же SQLite
   транзакции, без промежуточного `idle`, видимого reminder scheduler.
5. [x] Повторный запуск drill-tool не создаёт вложенный стек: интерфейс
   продолжает уже открытый временный drill.
6. [x] Пока бот ждёт фразу для перевода, due reminder не доставляется и
   становится доступен сразу после выхода из input mode.
7. [x] Миграция нормализует прежний `stage=toolkit_input` в overlay-модель;
   существующие данные и активные учебные sessions сохраняются.
8. [x] Integration tests покрывают перевод поверх scenario, карточки поверх
   scenario, карточки поверх drill, atomic restore и reminder isolation.

## 20. OpenAI-first failover и доступные инструменты — реализовано 2026-08-02

Причина изменения: Gemini начал отвечать `HTTP 429`, поэтому мастерская
показывала `ИНСТРУМЕНТ НЕДОСТУПЕН`, хотя learner state и навигация работали
корректно. Наличие инструмента теперь отделено от состояния одного AI-provider.

Реализовано:

1. [x] Добавлен `OpenAIClient` для Responses API со strict JSON schema,
   `store=false`, timeout/retry и явным `reasoning.effort`.
2. [x] Основной route — `gpt-5.6-sol` с effort `low`; Gemini остаётся вторым
   route. Порядок задают `AI_PROVIDER` и `AI_FALLBACK_PROVIDER`.
3. [x] `FailoverAIClient` сохраняет прежний `AIClient` contract, переключается
   только после `AIError` и временно размыкает circuit, чтобы не повторять
   заведомо падающий primary на каждом действии.
4. [x] Карточки и тематические тренировки имеют локальный curated fallback:
   пять карточек с четырьмя вариантами либо пять заданий минимум трёх типов и
   двух active-recall items. Они доступны даже без внешнего AI.
5. [x] Произвольный перевод по-прежнему требует хотя бы одного AI-provider;
   при отказе primary автоматически проверяется secondary, learner state не
   теряется и ввод можно повторить.
6. [x] Consent повышен до v3: ученик явно информируется, что минимальный учебный
   контекст может обрабатываться OpenAI или Google Gemini; Telegram ID и имя в
   AI prompt не передаются.
7. [x] Реальный OpenAI smoke подтвердил авторизацию, strict structured output,
   русско-польский перевод с двумя альтернативами, пять валидных карточек и
   анализ польского ответа с естественной формулировкой.
8. [x] Unit/integration/fallback/consent tests расширены; полный набор — 73
   теста, плюс `compileall` и `git diff --check`.
